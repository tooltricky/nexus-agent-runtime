# Nexus Agent Runtime：可执行的 AI 编程工作流

适用对象：主要通过 Codex 开发，希望独立完成项目、理解关键设计，并将项目用于面试的开发者。

核心循环：**一张任务卡 → 明确验收 → 小步实现 → 真实验证 → 独立审查 → 提交与复盘**。你负责目标、取舍和验收；Codex 负责调查、实现和提供可复查的证据。

## 1. 先认清项目现在的位置

本指南依据 `project-design.md`、ADR 0001～0003、README、现有测试和部分关键实现整理。本次没有运行项目或测试；下面的“已有”表示文档和代码中存在相应实现，不代表本次重新验证通过。

| 层次 | 当前含义 | 开发时怎样使用 |
| --- | --- | --- |
| 设计说明书 | 长期目标，包括多 Agent、模型、MCP、安全、观测和 Kubernetes | 用来检查方向与最终覆盖范围，不应一次性生成全部组件 |
| ADR 0001 | Java 21 / Spring Boot 模块化单体，PostgreSQL 是持久化事实来源 | 当前架构起点；不因长期架构图而提前拆成多个语言和服务 |
| ADR 0002 | 持久化租约，owner、有效期、乐观版本共同保护状态迁移 | 后续能力必须继续保护租约所有权 |
| ADR 0003 | 有限尝试、持久化退避、原子失败 | 租约过期进入 RETRYING 或 FAILED，替换 ADR 0002 的立即回到 PENDING 行为 |
| 代码与测试 | 当前实际行为及其验证手段 | 与已接受 ADR 不一致时，记录差异，再决定修代码还是新增 ADR |

当前已经有：Session/Run 创建、请求幂等、固定 Task、fake executor、租约回收、失败退避、有序事件时间线，以及相关状态机和数据库集成测试。

当前仍是 fake worker 纵向切片；真实模型、工具、DAG、审批、鉴权和 Kubernetes 等属于后续工作。`tasks` 目前存在 `one_task_per_run` 唯一约束，DAG 需要显式迁移和新的 Run 聚合规则。当前事件表用于审计与集成日志，系统不是事件溯源架构。

**工作约定：**当前任务要求必须与已接受 ADR 对齐；修改既有决策时新增 ADR，注明替换关系。历史 ADR 记录当时的决策，不通过改写历史来掩盖行为变化。

## 2. 一次性建立最少的项目记忆

建议逐步添加以下文件；本指南只提供模板，没有替你创建这些文件或改变现有协作规则。

```text
AGENTS.md                    # 每次开发都适用的简短约束与验证命令
docs/backlog.md              # 里程碑、任务顺序、依赖、当前状态
docs/tasks/T-xxxx.md         # 单张任务的目标、验收与交接记录
docs/evidence/              # 里程碑演示、故障演练和测量结果
```

继续复用现有 README、ADR 和 `packages/contracts`，不再复制一份完整架构说明。文件间以链接引用，减少多个版本互相冲突。

可作为根目录 `AGENTS.md` 的初稿：

```markdown
# 项目约定
- 先读 README、当前任务卡、相关 ADR，再定位相关代码与测试。
- 当前采用 Java 21 / Spring Boot 模块化单体和 PostgreSQL。
- docs/project-design.md 是长期目标；当前实现范围以已接受 ADR 为依据。
- ADR 0003 替换 ADR 0002 中租约过期立即回到 PENDING 的规则。
- 状态与相应事件必须在同一事务提交；domain_events 保持 append-only。
- max_attempts 包含首次尝试；attempt 只在领取租约时增加。
- Worker 写回必须检查 owner、状态、当前版本和未过期租约。
- 租约及重试资格使用数据库时钟；迟到、重复报告不得产生新事件。
- 数据库及事件写入异常必须回滚，不能吞掉并当成执行失败。
- 修改已应用的数据库结构应增加 Flyway migration，不改写历史 migration。
- API、状态和事件变化要检查 OpenAPI、JSON Schema、测试和 README。
- 当前一 Run 一 Task；增加 DAG 前先明确新的聚合终态规则。
- 不把外部副作用宣称为 exactly-once；为具体操作设计稳定幂等键。
- 只完成当前任务；依赖变更、服务拆分和额外重构应说明必要性。

# 验证
- 单元测试可通过 README 中的 Maven 容器命令运行。
- 数据库行为使用 deploy/docker-compose.test.yml 中的独立测试库验证。
- TEST_DB_URL 缺失会跳过数据库集成测试，不能据此宣称完整通过。
- 报告实际命令、结果、测试数和跳过数；区分通过、失败、未执行。
- 不用开发数据卷运行破坏性测试。
```

保持这份文件简短。某个功能的详细语义放任务卡；关键规则由测试、数据库约束和 CI 检查执行，文字约定本身不构成质量保障。

## 3. 每张任务卡都使用这个模板

```markdown
# T-xxxx：一个可观察的行为
状态：待规划 / 可实施 / 实施中 / 待审查 / 完成 / 阻塞

## 问题与目标
现在发生什么？本次完成后，用户或系统能观察到什么变化？

## 依据与入口
关联 ADR、相关文件或类、已有测试、依赖任务。
如需改变已有决策：链接新 ADR 草案。

## 本次边界
列出本次行为，以及会留到后续任务的相关能力。

## 验收
- Given 某状态，When 某动作，Then 某状态、返回值和事件。
- 至少覆盖相关失败路径；涉及并发时明确竞争的合法结局。
- 明确不得发生的副作用或额外事件。

## 实现计划
最少改动、事务边界、兼容性、迁移方式、验证命令。

## 完成记录
提交、实际变更、验证结果与跳过项、演示方法、剩余问题。
```

任务大小以“你能理解、审查并演示一个行为”为准。通常一个任务对应一个小 PR；复杂功能可以拆成多个依赖任务。不要按“实现整个 Worker”“补完安全模块”这样的模块名称派工，也不要为了控制行数而拆散必要的实现和测试。

## 4. 每次开发照这个顺序执行

| 步骤 | 你做什么 | Codex 交付什么 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 1. 选任务 | 从 backlog 选一个有依赖顺序的行为 | 当前能力、缺口、相关文件和不确定项 | 目标可用一两句话说明 |
| 2. 写验收 | 确认正常、失败、竞争时应发生什么 | 任务卡和有依据的最小计划 | 你能解释验收条件 |
| 3. 建基线 | 确认工作区状态，建立功能分支 | 现有检查结果与历史失败项 | 能区分已有问题和本次问题 |
| 4. 实现 | 检查是否偏离任务 | 聚焦的代码、必要迁移、合约和测试 | 一个行为闭环，无无关重构 |
| 5. 验证 | 查看执行证据，实际跑一次演示 | 命令、退出码、报告、状态及事件结果 | 对应检查真实通过，没有关键跳过项 |
| 6. 审查 | 用新会话审查差异，再判断问题 | 文件位置、触发条件、影响及复现办法 | 已处理阻断问题，剩余风险明确 |
| 7. 提交 | 确认要提交的文件，合并小 PR | 说明问题、变化、验证的提交或 PR | 可回到一个已验证的提交 |
| 8. 复盘 | 讲清调用链、取舍和失败处理 | 更新任务状态、交接与证据 | 下一次无需依赖旧聊天记录 |

小文案、注释等低风险修改可以简化流程。状态机、SQL 并发、迁移、租约、权限和外部副作用必须完整走验收与审查。

基线、版本控制和检查可从这些命令开始：

```bash
git status --short
git switch -c feat/T-xxxx-short-description
git diff --stat
git diff --check
git diff
```

有未提交改动时先辨认来源，不让 Codex 覆盖或清理未知改动。检查差异、选定文件后再提交，不机械地把整个工作区全部暂存。共享历史的回退优先采用针对性 revert；数据库回退还需要单独判断数据与 schema 兼容性。

## 5. 可以直接复制的提示词

### A. 任务开始：先调查和规划

```text
请阅读 README.md、相关 ADR、任务卡 [路径]，并定位必要的代码和测试。
本次目标：[一个具体行为]。
先不修改代码，输出：
1. 当前行为与依据的文件位置；不要把目标设计当成已实现。
2. 正常、失败、竞争路径的验收条件。
3. 最小实现计划、事务边界、合约与迁移影响。
4. 实际可用的验证命令，以及环境依赖或可能跳过的测试。
5. 需要我决定的设计取舍；常规实现细节给出你的推荐。
若工作量过大，拆成有依赖顺序、各自可验收的小任务。
```

### B. 实施：给自主性，也给完成标准

```text
按任务卡 [路径] 和刚确认的计划完成当前任务。
先检查工作区和相关测试基线，再实现最小闭环。
逻辑缺陷先添加可复现的失败测试；新功能以验收场景设计测试。
数据库并发与事务行为用真实 PostgreSQL 集成测试验证。
执行对应检查，修复本次引入的问题；不要靠删除断言、跳过测试来过关。
发现无法满足的架构约束时先报告证据和方案，不临时改变验收语义。
完成后报告：改动、验证命令与结果、通过/失败/跳过数量、演示步骤、剩余风险。
不要自动开始下一个任务。
```

### C. 新会话审查：让审查者寻找反例

```text
请只审查，不修改代码。
依据任务卡 [路径]、相关 ADR 和实际 git diff，独立检查本次变化。
若已提交，先确定本次任务的比较基点；不要默认 HEAD 就是基点。
优先检查：状态与事件的事务一致性、owner/version/有效期、并发竞争、
重复报告、重启恢复、失败重试、副作用幂等、迁移与 API 兼容。
检查测试有没有真的执行，是否只验证实现细节或遗漏失败路径。
每项问题给出严重程度、文件位置、触发条件、影响和可验证的复现办法。
区分确认缺陷、待验证风险与风格意见；没有发现问题就如实说明审查范围。
不要为了凑数量制造问题，也不要把实现者的“已通过”当成证据。
```

单人开发也可以顺序使用“实现会话”和“审查会话”，不需要一开始配置多 Agent。新的 AI 会话仍可能犯同类错误；测试、实际演示和你的判断继续保留。

### D. 失败排查：避免补丁越打越大

```text
当前命令：[命令]；完整错误：[相关日志]；最近变化：[提交或差异]。
先给出可验证的根因假设和最小复现，再修改。
区分代码问题、测试问题、依赖问题与环境问题。
如果同一问题已经修了两轮仍失败，请停止扩散改动，
列出已尝试办法与证据，缩小复现；只修根因并重跑相关检查。
```

### E. 交接：保存事实，而非保存整段聊天

```text
把当前进度更新到任务卡：目标、分支与提交、已改文件、关键决策、
已执行的命令及结果、未执行或跳过项、未解决问题、下一条具体行动。
随后给我一段新会话可直接使用的接续提示词。
不要把推测写成结论，不复制密钥或含敏感信息的完整日志。
```

### F. 学习：检验自己是否掌握本次改动

```text
围绕刚完成的任务，带我从 API/调度入口追踪到数据库和事件写入。
先让我自己解释关键设计，再指出错误，并给出对应代码位置。
用 3 个故障或竞争场景提问；先不要给答案。
最后告诉我面试时应该能独立解释的概念和一个最小练习。
```

## 6. 为当前项目设置真实的验证门槛

README 已提供两种测试入口。单元测试可以使用 Maven 容器：

```bash
docker run --rm \
  -v "$PWD/services/control-plane:/workspace" \
  -w /workspace \
  maven:3.9.11-eclipse-temurin-21 mvn -B test
```

**该命令没有配置 TEST_DB_URL，因此数据库集成测试会跳过。**涉及 SQL、事务、租约、失败恢复的变更，使用独立测试环境：

```bash
docker compose -f deploy/docker-compose.test.yml up --abort-on-container-exit --exit-code-from tests
```

记录上一个命令的退出状态和测试日志，再清理测试容器：

```bash
docker compose -f deploy/docker-compose.test.yml down
```

CI 必须保留测试步骤的失败状态，不能用成功的清理命令覆盖它。测试报告在 `services/control-plane/target/surefire-reports/`，核对本次相关测试是否实际运行以及 skipped 数量。不要把“0 failures、但集成测试全部 skipped”记为数据库验证通过。

现有测试环境会清空业务表，必须使用独立数据库；不要把 TEST_DB_URL 指向开发数据或真实数据。

| 变更类型 | 必要证据 |
| --- | --- |
| 状态机、退避公式 | 单元测试，包含非法迁移、边界值与溢出 |
| 租约、SQL、失败恢复 | 真实 PostgreSQL，重复/迟到/竞争/回滚/重启相关场景 |
| API 或事件 | 响应和真实事件经过合约校验，并检查兼容性 |
| 模型或工具适配器 | 离线桩测试错误路径；少量真实调用作为单独 smoke test |
| 审批与授权 | 允许、拒绝、过期、跨租户与参数变更的负向测试 |
| DAG | 依赖解锁、失败传播、重启恢复、部分成功与取消 |
| 性能优化 | 固定环境、负载、数据、版本和可复现测量脚本 |

表中部分门槛是后续需要建立的能力。仓库里有 OpenAPI/JSON Schema 文件，并不自动意味着存在执行这些文件的合约测试。

第一张工程任务建议是：**让 CI 运行已有完整测试并明确报告关键集成测试是否跳过**。优先复用现有 Compose 测试环境，不为此先更换测试框架。之后单独补 Session/Run API、幂等键重复与冲突、并发请求和事件合约测试，避免一个“补质量”任务无限扩大。

测试修复后可在同一任务分支继续，不必重走所有流程；只有新增改动、失败或新风险才扩大验证范围。覆盖率可以辅助找空白，不能替代对租约和事务不变量的检查。

## 7. 随代码增长，怎样控制上下文与任务范围

- 一个会话围绕一张任务卡。可在同一会话完成实现与修复，审查时开新会话。
- 入口提供 README、任务卡和相关 ADR，让 Codex 自己定位相关文件；不必每次读取整个仓库。
- 不相关的新功能、连续错误假设或明显跑偏时，先更新任务卡，再开新会话。
- 稳定约束进入 AGENTS.md，架构取舍进入 ADR，临时进度进入任务卡，长期待办进入 backlog。
- 修改公共接口时，要求 Codex 搜索所有调用方和合约，不能只改当前文件。
- 新能力优先延续现有分层；确有变更压力时再进行独立重构，避免每次功能开发都重写架构。
- 自动格式化、检查和 CI 稳定后再考虑 skills、MCP、自动化或并行会话；工具数量不是进度指标。

默认一次只推进一个实现任务。未来确需并行时，应按无交叉写入的任务划分，用独立 worktree，并预先确定 API/事件合约；不要让多个实现会话同时修改租约状态机或同一组迁移。

## 8. 适合本项目的实现顺序

下面按依赖和验收门槛推进，不承诺在固定八周内完成所有企业平台能力。

| 阶段 | 建议任务顺序 | 阶段出口 |
| --- | --- | --- |
| P0：稳定现有切片 | CI 全量验证 → API/幂等/事件合约补缺 → 可重复演示脚本 | 新环境能启动；现有成功、重试与耗尽路径有可核查证据 |
| P1：支撑真实长任务 | 执行事务边界 → 租约续期 → 超时 → 取消；每项分别定语义和测试 | 慢任务不长期占用数据库事务；崩溃可回收；迟到结果不能覆盖终态 |
| P2：真实 Agent 最小闭环 | 单模型适配器 → 受控的结构化工具调用 → 一个只读 MCP 工具 → 工具调用记录、超时与预算 | 一条可解释的“模型—工具—结果”链路，CI 不依赖真实付费模型 |
| P3：治理后接入写工具 | 身份与租户隔离 → 授权策略 → Approval → 参数绑定、短期凭证、审计 → 沙箱工单写入和幂等 | 越权/过期/篡改被拒绝；重复执行不重复创建工单 |
| P4：持久化多任务与编排 | 多 Task schema/终态规则 → 固定 DAG → 三个 Specialist → 有边界的 SuperAgent 计划与消息 | 重启后依赖仍正确；失败传播明确；模型不能越过权限和工具边界 |
| P5：观测、回放与评测 | 早期埋点汇总为 OTel/日志/指标 → 回放录制 → Console → 固定评测集 | 能定位一个失败节点，离线回放不触发真实副作用，并输出质量与成本报告 |
| P6：弹性与平台化 | 独立 Worker 边界 → Kubernetes 隔离 → KEDA → 配额/背压/公平调度 → 故障演练与压测 | 用脚本证明隔离、扩缩容和恢复；明确性能与资源条件 |

观测字段、工具审计和模型费用记录应随相应功能加入，P5 再统一呈现；不能等到最后才补证据。P6 之前，本地和 CI 也要保持工具权限与执行边界。

若要覆盖设计说明书的完整目标，P6 后还应逐项核对：服务间身份和 mTLS、凭证撤销、数据脱敏/保留/删除、模型熔断与降级、队列公平与费用限额等。Kafka/outbox、Redis、ClickHouse、MinIO、Vault、独立 Go/Python/TypeScript 服务应按具体需求和 ADR 引入；若选择暂缓，应在范围表中标明，不能把它们算作已经完成。

为长期目标维护一张覆盖表：`设计章节 → 任务 → 未开始/部分/完成/延期 → 验收证据`。求职版本可以先完成稳定的核心演示，完整平台按后续阶段继续推进；README 和简历必须与实际交付范围一致。

### 接入真实模型前，必须先处理的具体问题

目前 `FakeWorkerService.advanceOneTask()` 带有 `@Transactional`，并会沿调用链执行 `TaskExecutor.execute()`；任务也在事务内被锁定。当前固定输出很快，这与 fake worker 的范围相符。直接换成慢模型调用会延长事务与行锁持有时间，影响回收、连接资源及取消等行为。

建议先新增 ADR，明确：

1. 用短事务领取或推进任务，并提交状态与事件。
2. 在数据库事务之外执行模型或工具调用。
3. 用短事务检查当前租约、owner、版本后写回结果与事件。
4. 明确续租如何与写回竞争，特别是续租更新版本时的协调方式。
5. 定义取消/超时与成功竞争的合法结果，以及取消后仍可能运行的外部调用如何处理。

提交保护只能阻止过期结果写入数据库，不能撤销已经发生的外部操作。写工具必须另有稳定的操作幂等键、去重或对账策略。租约接管是任务恢复机制，不等于外部副作用只发生一次。

### 第一项租约续期任务可以这样写

```text
目标：仍持有有效租约的 worker 可以续租，避免正常慢任务被错误回收。

验收：
- owner、当前版本、状态和有效期符合条件时，基于数据库时钟延长有效期。
- 外来 owner、过期租约、旧版本和终态任务均不能续租。
- 续租不增加 attempt，不改变 max_attempts 和 next_attempt_at。
- 续租与 watchdog 竞争后，只出现协议允许的一种一致结果。
- 定义续租是否记录事件；不得把 heartbeat 噪声误作任务状态迁移。
- 定义续租与执行结果写回之间的版本协调，避免正常结果持续被拒绝。
- 在真实 PostgreSQL 中验证上述条件，保留现有重试行为。

依赖：先完成事务边界任务；先写 ADR 明确协议，再按小任务实施。
```

不要直接把这个例子作为已经决定的协议。特别是取消、续租、失败分类和 jitter，ADR 0003 明确留给后续决策；引入它们时新增 ADR 和测试，不顺带改变现有语义。

## 9. 每个里程碑积累面试能用的证据

每阶段保存一份精简记录：代码版本、运行环境、操作脚本、预期结果、实际状态/事件、关键截图、测量口径和限制。日志先脱敏，不把模型密钥、Token 或私有工具数据纳入仓库。

至少准备三个能复现的场景：

1. 同一幂等键重复创建只得到一个 Run；不同请求使用同一键返回冲突。
2. Worker 在领取或执行时停止，任务按租约和退避恢复，迟到写回被拒绝。
3. 重试额度耗尽，Task 与 Run 原子失败，事件时间线与状态一致。

权限、Replay 和多 Agent 完成后再增加对应演示。故障注入优先通过测试替身、可控执行器或演示配置实现，不靠手改数据库制造“恢复成功”。

模型评测逐步建立设计说明书中的固定 30 条诊断样本，保留输入、期望证据、评分规则、模型与提示版本，分别报告任务成功率、证据完整度、Token 成本和人工介入率。离线 CI 负责确定性回归，真实模型评测单独运行并记录成本；录制工具响应的 Replay 也不保证重新调用模型会产生完全相同的答案。

每张卡结束后，自己不看 AI 答案解释五件事：问题是什么、为何采用此方案、代码调用链、失败/竞争如何处理、测试证明了什么以及没证明什么。讲不清楚就继续追踪相关代码，并亲手运行或调整一个最小场景。

面试需要重点掌握的当前概念：事务、行锁与 SKIP LOCKED、乐观版本、数据库时钟、租约、退避、幂等、状态与事件原子提交，以及它们对外部副作用的限制。

代码由 Codex 生成，不妨碍你通过真实的需求定义、设计取舍、验收和排错形成个人贡献。介绍时如实说明使用 AI 辅助开发，并能具体说明自己的决策与验证工作。

简历表述示例，使用前先完成并保留对应验证证据：

> 基于 Java 21、Spring Boot 与 PostgreSQL 实现 Agent Runtime 核心纵向切片，支持 Run 幂等创建、持久化任务租约、有限重试和事件时间线；通过数据库集成测试验证迟到写回、竞争恢复及失败状态与事件的事务一致性。

未实现 Kubernetes、真实多 Agent 或权限治理时不写已支持；设计中的“50 并发”“p95 冷启动 < 8 秒”属于目标，只有完成可复现测量后才转为成果。性能报告同时保留版本、机器、样本量、预热方式、成功定义和原始数据。

## 10. 从下一次开发开始怎么做

1. 用本指南模板建立简短 AGENTS.md 和 backlog，把上述阶段映射为任务，不进行全面重写。
2. 第一张任务卡只做现有测试的 CI 门槛与报告，验证关键集成测试没有被跳过。
3. 第二张任务卡调查并补齐 API/幂等/合约中最重要的一项缺口。
4. 第三张任务卡起草执行事务边界 ADR，再拆实现与竞争验证。
5. 每张卡按“规划—实现—验证—新会话审查—提交—复盘”循环推进。
